`px` is an ordinary command-line tool for your Phoenix instance. You run it yourself, and because it needs nothing but a shell, any coding agent can run it too, which is what makes it the simplest way to give one access to your traces. The [`phoenix-cli` skill](/docs/phoenix/integrations/developer-tools/skills) is what teaches an agent which of these commands to reach for.

Not connected yet? [Observe Your Agent](/docs/phoenix/get-started/get-started-tracing) covers `px setup`, which wires a project to Phoenix and waits for a real trace.

## Install

```bash
# run any command without installing
npx -y @arizeai/phoenix-cli trace list

# or install once
npm install -g @arizeai/phoenix-cli
```

Point it at your instance with `PHOENIX_ENDPOINT`, plus `PHOENIX_API_KEY` if auth is on:

```bash
export PHOENIX_ENDPOINT=http://localhost:6006
```

## Debugging a failure

Whether you type these or an agent does, a pass runs in the same order.

**1. Narrow to the failures.** This prints the trace and span ids the next step needs.

```bash
px span list --project my-app --status-code ERROR --limit 10
```

Swap `--status-code ERROR` for `--span-kind LLM` to look at model calls instead, and add `--format json` to pipe results into `jq` rather than reading a table. Set `PHOENIX_PROJECT` once to drop `--project` everywhere.

**2. Open one in full.** A trace expands into every span inside it, with inputs, outputs, and timing.

```bash
px trace get 3b59e7fdc86dd3d8ccf951403882b5ec --project my-app
```

**3. Record what you found,** so it stays attached to the trace for whoever opens it next.

```bash
px span annotate 6099f08961d12ae9 --name correctness --label incorrect --score 0
px trace add-note 3b59e7fdc86dd3d8ccf951403882b5ec --text "Tool called with an empty query"
```

Both take the OpenTelemetry id, 16 hex characters for a span and 32 for a trace. That is `context.span_id` and `context.trace_id` in `px span list --format json`, and not the opaque id shown elsewhere. Pass `--identifier` to have a repeat call overwrite its own annotation instead of stacking another.

**4. Fix it in the code.** `px` stops here, and annotations plus notes are the whole of what it writes. The agent is already in your editor, so the change goes there; your next run sends fresh traces to Phoenix, and step 1 starts again.

## Checking a change

`px` reads datasets, experiments, and prompts so an agent can see what a change is measured against. It cannot create or edit them: build a dataset and run an experiment from the UI, as in [Evaluate Your Agent](/docs/phoenix/get-started/get-started-evaluations), or in code with the SDK.

```bash
px dataset list                              # names, ids, and example counts
px dataset get travel-support                # the examples inside one dataset
px experiment list --dataset travel-support  # runs against that dataset
px experiment get RXhwZXJpbWVudDoxMQ==       # per-example scores from one run
px prompt get my-prompt                      # the prompt's current version
```

Experiment ids are opaque, as above, so take them from `experiment list`. Datasets and prompts also accept their name.

## Everything else

| Command | What it manages |
| --- | --- |
| `px project` | Projects |
| `px session` | Multi-turn sessions |
| `px annotation-config` | Annotation label schemas |
| `px trace-annotations`, `px span-annotations`, `px session-annotations` | Bulk deletion of stored annotations. Each takes only `delete`, needs `--all` or a `--start-time`/`--end-time` window, and refuses to run unless `PHOENIX_CLI_DANGEROUSLY_ENABLE_DELETES=true` is set. |
| `px api graphql` | Read-only GraphQL queries against the Phoenix API. Mutations are rejected. |
| `px docs` | Workflow docs for coding agents |
| `px auth`, `px profile` | Credentials and saved endpoints |
| `px self` | The installed CLI |

Run `px <command> --help` for the flags on any of them.

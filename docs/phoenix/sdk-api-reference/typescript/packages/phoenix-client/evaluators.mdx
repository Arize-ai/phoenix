The evaluators module manages shared evaluator definitions and the bindings that attach them to datasets and projects. A definition is shared by every binding that references it, so an update applies everywhere the evaluator is used.

Every helper requires a Phoenix server on 21.0.0 or later. Each one checks the server version before its request and throws against an older server.

## Evaluator Kinds

| Kind | How it is created | Dataset bindings | Project bindings | Edit and delete |
|------|-------------------|------------------|------------------|-----------------|
| `llm` | `createEvaluator`, pinned to an existing prompt version | By reference | By reference | `updateEvaluator`, `deleteEvaluator` |
| `code` | `createEvaluator`, with its first version | By reference | By reference | `updateEvaluator`, `createCodeEvaluatorVersion`, `deleteEvaluator` |
| `builtin` | Ships with Phoenix | By reference | Not accepted | Never edited or deleted |

Create a definition first, then bind it by its `id`. One definition can back any number of bindings, and deleting a binding never deletes the definition.

## Errors

Failed requests throw an `HttpError`. When the server explains the failure, `error.problem` holds its [RFC 9457](https://www.rfc-editor.org/rfc/rfc9457) problem details. A name clash is refused with `409`, `code` `already_exists`, and `existing_id` naming the resource that holds the name, so an agent can reuse it instead of retrying.

```ts
import { HttpError } from "@arizeai/phoenix-client";
import { createEvaluator } from "@arizeai/phoenix-client/evaluators";

try {
  await createEvaluator({ evaluator });
} catch (error) {
  if (error instanceof HttpError && error.problem?.code === "already_exists") {
    console.log("reusing", error.problem.existing_id);
  } else {
    throw error;
  }
}
```

`problem.type` publishes `code` as `urn:phoenix:problem:<code>`: `validation_error`, `invalid_argument`, `not_found`, `already_exists`, `conflict`, `forbidden`, `insufficient_storage`, or `error`. Treat a `code` you don't recognize by `error.status` — new codes are additive.

`problem.reason` is a finer condition under `code`, present on some `conflict` responses. Treat a `reason` you don't recognize by `code` alone. The reasons today, and what to do for each:

- `still_bound` (deleting a definition something still binds): detach the bindings first, then delete.
- `incompatible_override` (an edit would leave a dataset binding's override outputs unsupported by the prompt it now runs): fix or clear the listed overrides.
- `version_mismatch` (`expected_current_version_id` didn't match): re-read the evaluator and reconcile before retrying — never blindly resubmit with the version the error reports as current, since another deploy can land before you do.
- `concurrent_change` (another write touched the same row mid-request): retry the same request unchanged.

The recovery fields on `problem`, present only for the `reason` (or, for `existing_id`, `code`) named:

- `existing_id` (`already_exists`): the GlobalID of the resource holding the name.
- `current_version_id` (`version_mismatch`): the GlobalID of the version actually current, or `null` when the evaluator has none yet.
- `binding_counts` (`still_bound`): `{ project: number, dataset: number }`, how many of each kind still refuse the delete.
- `dataset_evaluator_ids` (`incompatible_override`): GlobalIDs of the dataset bindings whose overrides no longer fit.

`problem.detail` is a human-readable explanation, not meant to be parsed; branch on `code` and `reason`, never on the text of `detail`.

Not every failure is problem details shaped this way. A 401 is a plain-text authentication challenge. An unhandled 500, or a proxy sitting in front of Phoenix, can return a body that isn't JSON at all. In every case `error.status` and `error.statusText` are still the real HTTP status, and `error.problem` is `undefined` when the body didn't parse as one.

## List And Read Definitions

```ts
import {
  getEvaluator,
  getEvaluators,
} from "@arizeai/phoenix-client/evaluators";

for (const evaluator of await getEvaluators({ type: "builtin" })) {
  console.log(evaluator.id, evaluator.name);
}

const evaluator = await getEvaluator({ evaluatorId: "Q29kZUV2YWx1YXRvcjoy" });
if (evaluator.type === "code") {
  console.log(evaluator.current_version_id, evaluator.source_code);
} else if (evaluator.type === "llm") {
  // `selector.type` is `version` when pinned, or `latest` for an evaluator
  // that follows the prompt's newest version
  console.log(evaluator.prompt.selector, evaluator.prompt.resolved_prompt_version_id);
}
```

`getEvaluators` follows pagination to the end. Every item embeds its current code or prompt version, so pass `name` or `limit` when you are looking for one evaluator.

## Create An LLM Evaluator

`createEvaluator` with `type: "llm"` pins an existing prompt version. Create the prompt with `createPrompt` from the [prompts](./prompts) module first.

```ts
import { createEvaluator } from "@arizeai/phoenix-client/evaluators";

const evaluator = await createEvaluator({
  evaluator: {
    type: "llm",
    name: "toxicity",
    description: "toxicity",
    prompt: {
      selector: { type: "version", prompt_version_id: "UHJvbXB0VmVyc2lvbjo3" },
    },
    output_configs: [
      {
        type: "CATEGORICAL",
        name: "toxicity",
        optimization_direction: "MINIMIZE",
        values: [
          { label: "toxic", score: 1 },
          { label: "clean", score: 0 },
        ],
      },
    ],
  },
});
```

- The `description` must equal the description of the prompt's tool function, and the output configs must be categorical and match that tool.
- The name must be unique among evaluators; a clash is refused with `409` and `already_exists`.
- Creating the evaluator adds the `evaluator` label to the prompt and creates a tag that pins the version; the prompt is otherwise unchanged.

## Create A Code Evaluator

`createEvaluator` with `type: "code"` creates a code evaluator and its first version. `getSandboxConfigs` lists the sandboxes it can run in; pick one whose `is_usable` is `true`.

```ts
import { readFile } from "node:fs/promises";

import {
  createEvaluator,
  getSandboxConfigs,
} from "@arizeai/phoenix-client/evaluators";

const [sandbox] = (await getSandboxConfigs({ language: "PYTHON" })).filter(
  (config) => config.is_usable
);

const evaluator = await createEvaluator({
  evaluator: {
    type: "code",
    name: "exact-match",
    source_code: await readFile("evaluator.py", "utf8"),
    language: "PYTHON",
    sandbox_config_id: sandbox.id,
    input_mapping: { literal_mapping: {}, path_mapping: { output: "output" } },
    output_configs: [
      { type: "CONTINUOUS", name: "score", optimization_direction: "MAXIMIZE" },
    ],
  },
});
```

`output_configs` needs at least one entry. The name must be unique among evaluators; a clash is refused with `409` and `already_exists`.

## Deploy A Code Version

Code is immutable per version. `createCodeEvaluatorVersion` appends new source and applies any `configuration` (sandbox, input mapping, outputs, or description) in the same transaction, so bindings never run the new code with the old configuration.

```ts
import { readFile } from "node:fs/promises";

import {
  createCodeEvaluatorVersion,
  getEvaluator,
} from "@arizeai/phoenix-client/evaluators";

const current = await getEvaluator({ evaluatorId: "Q29kZUV2YWx1YXRvcjoy" });
if (current.type !== "code") throw new Error("Expected a code evaluator");

const version = await createCodeEvaluatorVersion({
  evaluatorId: current.id,
  sourceCode: await readFile("evaluator.py", "utf8"),
  expectedCurrentVersionId: current.current_version_id ?? undefined,
  configuration: {
    output_configs: [
      { type: "CONTINUOUS", name: "score", optimization_direction: "MAXIMIZE" },
    ],
  },
});
console.log(version.id, version.was_created);
```

- `expectedCurrentVersionId` is optional. When another version has been appended since, the server refuses the stale deploy with `409` instead of deploying over it.
- If the source matches the current version, the existing version is returned and `was_created` is `false`. Only the current version is compared, so restoring older source creates a new version.
- `getCodeEvaluatorVersions` lists the versions, newest first.

## Update A Definition

```ts
import { updateEvaluator } from "@arizeai/phoenix-client/evaluators";

await updateEvaluator({
  evaluatorId: "Q29kZUV2YWx1YXRvcjoy",
  patch: { type: "code", description: "Exact match against the expected output" },
});

await updateEvaluator({
  evaluatorId: "TExNRXZhbHVhdG9yOjE=",
  patch: {
    type: "llm",
    prompt: {
      selector: { type: "version", prompt_version_id: "UHJvbXB0VmVyc2lvbjo3" },
    },
  },
});
```

The `patch` is discriminated by `type`, which must match the evaluator, and needs at least one other field. Omitted fields keep their values.

- Prompt content is edited through the [prompts](./prompts) module: create a version with `createPrompt` and select it with `prompt: { selector: { type: "version", prompt_version_id } }`. A version of another prompt moves the evaluator to that prompt.
- An LLM evaluator's `description` must equal the description of its prompt's tool function.
- An LLM change that would invalidate a dataset binding's output overrides is refused with `409`.

## Delete A Definition

```ts
import { deleteEvaluator } from "@arizeai/phoenix-client/evaluators";

await deleteEvaluator({ evaluatorId: "Q29kZUV2YWx1YXRvcjoy" });
```

`deleteEvaluator` deletes an LLM or code evaluator that nothing binds. A code evaluator goes with its version history; an LLM evaluator goes with the tag that pins its version, and its prompt is kept. A definition still bound by a project or dataset is refused with `409`: delete those bindings first. Built-in ids are refused with `422`. A missing evaluator is ignored.

## Bind To A Dataset

A dataset binding registers an existing evaluator definition to run against the dataset's experiments. It does not run an experiment by itself.

```ts
import { createDatasetEvaluator } from "@arizeai/phoenix-client/evaluators";

const binding = await createDatasetEvaluator({
  dataset: { datasetName: "golden-questions" },
  name: "exact-match",
  evaluatorId: "Q29kZUV2YWx1YXRvcjoy",
  inputMapping: { literal_mapping: {}, path_mapping: { output: "output" } },
});
```

- Select the dataset with `datasetName`, `datasetId`, or the shorthand `dataset`, which accepts either.
- `evaluatorId` names an LLM, code, or built-in definition.
- The input mapping lives on the binding and is required.
- A name the dataset already uses is refused with `409` and `already_exists`.

## Override A Dataset Binding

`description` and `outputConfigs` on a binding are overrides. Omit them on create, or set `description` or `output_configs` to `null` in an update, and the binding uses the evaluator's values and follows later changes to them.

```ts
import { updateDatasetEvaluator } from "@arizeai/phoenix-client/evaluators";

await updateDatasetEvaluator({
  datasetEvaluatorId: "RGF0YXNldEV2YWx1YXRvcjox",
  patch: {
    output_configs: [
      { type: "CONTINUOUS", name: "score", optimization_direction: "MAXIMIZE" },
    ],
  },
});

// Drop the override and follow the evaluator's outputs again
await updateDatasetEvaluator({
  datasetEvaluatorId: "RGF0YXNldEV2YWx1YXRvcjox",
  patch: { output_configs: null },
});
```

- An `output_configs` override needs at least one config; `[]` is rejected.
- On an LLM evaluator, output overrides must be categorical and match the prompt's output tool, and a description override must equal that tool's description.
- `getDatasetEvaluator` and `getDatasetEvaluators` return the stored overrides; `null` means the binding uses the evaluator's value.

## Delete Dataset Bindings

```ts
import {
  deleteDatasetEvaluator,
  deleteDatasetEvaluators,
} from "@arizeai/phoenix-client/evaluators";

await deleteDatasetEvaluator({ datasetEvaluatorId: "RGF0YXNldEV2YWx1YXRvcjox" });

await deleteDatasetEvaluators({
  dataset: { datasetName: "golden-questions" },
  datasetEvaluatorIds: ["RGF0YXNldEV2YWx1YXRvcjoy", "RGF0YXNldEV2YWx1YXRvcjoz"],
});
```

Deleting a binding removes only the binding: its evaluator definition, prompt, and trace project are kept. `deleteDatasetEvaluators` deletes up to 1000 of a dataset's bindings atomically: either every binding is deleted or none is. Missing bindings are ignored, but an ID that is not a binding, or a binding of another dataset, fails the whole request.

## Run An Evaluator On A Project

A project binding runs an existing LLM or code evaluator definition on the project's incoming traces. Built-in evaluators cannot be bound to a project.

```ts
import { createProjectEvaluator } from "@arizeai/phoenix-client/evaluators";

// Evaluate a quarter of LLM spans as they arrive
await createProjectEvaluator({
  project: { projectName: "support-bot" },
  name: "exact-match",
  evaluationTarget: "SPAN",
  samplingRate: 0.25,
  evaluatorId: "Q29kZUV2YWx1YXRvcjoy",
  filterCondition: "span_kind == 'LLM'",
});

// Evaluate each trace once it has been quiet for 10 minutes
await createProjectEvaluator({
  project: { projectName: "support-bot" },
  name: "trace-exact-match",
  evaluationTarget: "TRACE",
  samplingRate: 1,
  evaluatorId: "Q29kZUV2YWx1YXRvcjoy",
  evaluationDelaySeconds: 600,
});
```

- `evaluationTarget` is `SPAN`, `TRACE`, or `SESSION`, and cannot change after the binding is created. `SPAN` evaluators run on matching sampled spans as they arrive. `TRACE` and `SESSION` evaluators run once per trace or session, after it has been quiet for the evaluation delay.
- `filterCondition` is written in the filter language of the target: a span filter for `SPAN`, a trace filter for `TRACE`, and a session filter for `SESSION`. A filter that does not compile is rejected with `422`.
- `samplingRate` is the fraction of matching records to evaluate, between 0 and 1.
- `evaluationDelaySeconds` applies to `TRACE` and `SESSION` targets only. It must be at least 10 seconds and defaults to 300 seconds. `SPAN` targets reject a delay and report `evaluation_delay_seconds` as `0`.
- `inputMapping` may be omitted to use the evaluator's own mapping. LLM evaluators have none, so their template variables bind to record fields of the same name.
- A binding is enabled unless you pass `enabled: false`.
- A name the project already uses is refused with `409` and `already_exists`.

## Update And Delete Project Bindings

```ts
import {
  deleteProjectEvaluators,
  updateProjectEvaluator,
} from "@arizeai/phoenix-client/evaluators";

// Pause the binding without deleting it
await updateProjectEvaluator({
  projectEvaluatorId: "UHJvamVjdEV2YWx1YXRvcjox",
  patch: { enabled: false },
});

await deleteProjectEvaluators({
  project: { projectName: "support-bot" },
  projectEvaluatorIds: ["UHJvamVjdEV2YWx1YXRvcjox"],
});
```

- On update, `input_mapping: null` drops the binding's mapping so the evaluator's applies; LLM evaluators have none, so their template variables bind to record fields of the same name. `evaluation_delay_seconds: null` restores the default delay. `filter_condition` is cleared with `""`, not `null`.
- `deleteProjectEvaluator` deletes one binding. `deleteProjectEvaluators` deletes up to 1000 of a project's bindings atomically, with the same rules as the dataset bulk delete. The definitions, prompts, and trace projects are kept.

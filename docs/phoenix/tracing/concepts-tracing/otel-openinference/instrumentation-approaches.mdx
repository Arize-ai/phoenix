Most AI applications use **hybrid instrumentation**: start with auto-instrumentation for supported SDKs and frameworks, then add manual spans where you need Phoenix to show application logic, context, or unsupported operations.

| Approach | Use when | What you get |
| :--- | :--- | :--- |
| **Auto-instrumentation** | Your provider or framework has an OpenInference integration | Model calls, messages, token counts, inputs, outputs, and framework spans |
| **Manual instrumentation** | You need spans around custom app logic | Tools, routing, retrieval, agent loops, eval steps, and unsupported SDKs |
| **Hybrid instrumentation** | You want a complete trace tree | Auto SDK spans nested inside manual app spans |

For setup steps, see [Auto-instrumentation](/docs/phoenix/tracing/how-to-tracing/setup-tracing/setup-using-phoenix-otel), [Manual instrumentation](/docs/phoenix/tracing/how-to-tracing/setup-tracing/instrument), and [Supported integrations](/docs/phoenix/integrations). This page explains how the approaches differ.

## Choosing an approach

A practical order:

1. **Start with [auto-instrumentation](/docs/phoenix/tracing/how-to-tracing/setup-tracing/setup-using-phoenix-otel)** when your model client, agent framework, or retrieval framework is supported.
1. **Add [manual spans](/docs/phoenix/tracing/how-to-tracing/setup-tracing/instrument)** for custom code, such as tools, routing, post-processing, or agent loops.
1. **Use [context managers](/docs/phoenix/tracing/concepts-tracing/otel-openinference/context-managers)** when the same context should apply to many spans, such as `session.id`, `user.id`, tags, or metadata.
1. **Use a [custom span processor](/docs/phoenix/tracing/concepts-tracing/otel-openinference/span-processor)** when you need centralized policy across every span, such as PII redaction or attribute enrichment.

The common production shape looks like this:

```text
CHAIN answer-question                  # manual span
  RETRIEVER search-docs                # manual or framework span
  LLM openai.chat.completions.create   # auto-instrumented span
  TOOL lookup-order                    # manual span
```

Manual spans give Phoenix the structure of your application. Auto-instrumented spans fill in the provider or framework details.

## Auto-instrumentation

Auto-instrumentation collects telemetry from supported libraries without per-call code changes. Use it whenever an OpenInference auto-instrumentor exists for your stack.

### Initialize an auto-instrumentor

```python
from phoenix.otel import register
from openinference.instrumentation.openai import OpenAIInstrumentor

tracer_provider = register(
    project_name="my-project",
    # api_key="..."  # Optional — only needed for instances with authentication enabled
)

OpenAIInstrumentor().instrument(tracer_provider=tracer_provider)
```

After this runs, every OpenAI call your application makes is traced. Phoenix receives the model name, input messages, output messages, token counts, and finish reason as attributes on an LLM span.

For the full list of supported frameworks and providers, see [Integrations](/docs/phoenix/integrations).

### How auto-instrumentors work

Auto-instrumentors wrap supported SDK and framework calls and emit OpenInference spans automatically. Phoenix then shows model calls, messages, token counts, errors, tool calls, and retrieval steps without you adding spans around every call.

For the source of every OpenInference instrumentor, see the [OpenInference repository](https://github.com/Arize-ai/openinference).

## Manual instrumentation

Manual instrumentation means creating spans with the OTel `tracer` and setting attributes with the [OpenInference semantic conventions](/docs/phoenix/tracing/concepts-tracing/otel-openinference/semantic-conventions).

The most common pattern uses `start_as_current_span` so the new span automatically becomes a child of the most recent active span in the OTel context:

```python
from opentelemetry.trace import Status, StatusCode
from phoenix.otel import register

tracer_provider = register(project_name="my-project")
tracer = tracer_provider.get_tracer(__name__)

query = "shipping status"
result = "order ships tomorrow"

with tracer.start_as_current_span("span-name") as span:
    span.set_attributes({
        "openinference.span.kind": "TOOL",
        "tool.name": "search",
        "input.value": query,
        "output.value": result,
    })
    span.set_status(Status(StatusCode.OK))
```

`start_as_current_span` does two important things:

1. It automatically sets the span as the active span in the OTel context, so any spans created inside the block become children.
1. It automatically calls `span.end()` when the context-manager block exits, so you don't have to manage span lifetime by hand.

Spans inherit the most recent active span as their `parent_id`, unless you set the context yourself.

### Pros and cons

| | |
| :--- | :--- |
| **Pros** | Full control. You decide what spans to create, what attributes to set, and how the tree is shaped. Works for any code, not just libraries the instrumentor supports. |
| **Cons** | Tracing an entire application by hand is tedious. Instrumentation code also lives beside your app code, which adds maintenance burden. |

### Common pitfalls

A few failure modes worth knowing about:

- **Forgetting to end a span**: spans are only handed off to the [span processor](/docs/phoenix/tracing/concepts-tracing/otel-openinference/span-processor) when `end()` is called. A never-ended span never exports. Use `start_as_current_span` because it ends the span when the block exits.
- **Not setting span status**: set `OK` or `ERROR` explicitly so the Phoenix UI can flag failures.
- **Missing important semantic conventions**:
  - `openinference.span.kind`: Phoenix uses this to pick the right icon.
  - `input.value` and `output.value`: Phoenix uses these in the trace list view.
  - `llm.input_messages` and `llm.output_messages`: Phoenix uses these to render chat history on LLM spans.
  - `tool.name` and `tool.parameters`: Phoenix uses these in tool detail panels.

For the practical how-to, see [Manual instrumentation](/docs/phoenix/tracing/how-to-tracing/setup-tracing/instrument). To add metadata, tags, users, sessions, or prompt template attributes, see [Customize your traces](/docs/phoenix/tracing/how-to-tracing/add-metadata/customize-spans).

## Hybrid instrumentation

Hybrid instrumentation combines auto-instrumentation with targeted manual spans. Use it when auto captures your SDK or framework calls, but you also need Phoenix to show your application logic.

Auto and manual spans nest together because they share the same OpenTelemetry context. When you open a manual span with `tracer.start_as_current_span(...)`, any auto-instrumented SDK call inside that block creates its span as a child.

```python
from opentelemetry.trace import Status, StatusCode

with tracer.start_as_current_span("answer-question") as span:
    span.set_attribute("openinference.span.kind", "CHAIN")
    span.set_attribute("input.value", question)

    response = client.chat.completions.create(
        model="gpt-4o-mini",
        messages=[{"role": "user", "content": question}],
    )

    span.set_attribute("output.value", response.choices[0].message.content)
    span.set_status(Status(StatusCode.OK))
```

In Phoenix, the manual `CHAIN` span is the parent. The OpenAI auto-instrumentor creates the nested `LLM` span for the model call.

Use hybrid instrumentation when:

| Gap | What to add |
| :--- | :--- |
| A supported SDK call is missing app context | Add a manual parent span around it |
| Your agent executes a Python or TypeScript function | Add a `TOOL` span |
| Your app routes, ranks, or post-processes data | Add `CHAIN`, `RETRIEVER`, or `RERANKER` spans |
| You need session, user, metadata, or tags across many spans | Use OpenInference context managers |

You can extend an auto-instrumented trace in three ways:

| Method | Pros | Cons |
| :--- | :--- | :--- |
| **Manually add spans** with `tracer.start_as_current_span()`. | Full control over what gets added. | Depending on the library, it can be hard to place the span in the right part of the trace tree. |
| **[OpenInference Context Managers](/docs/phoenix/tracing/concepts-tracing/otel-openinference/context-managers)** like `using_session`, `using_user`, and `using_metadata`. | No per-span code. Useful for context that applies to many spans, such as session ID. | Adds attributes to every span in scope, so it is less useful for per-span data. |
| **[Custom span processor](#custom-span-processor)**. | One place to enrich or filter every span. | More complex to write and review. |

## Custom span processor

Custom span processors give you one place to enrich or filter spans. Implement `on_start` and `on_end`, then attach the processor to the Tracer Provider.

What you can do at each hook:

| Hook | Span state | What it's good for |
| :--- | :--- | :--- |
| `on_start(span, parent_context)` | Mutable. Attributes may not be set yet, but name and span context can be edited. | Adding context-scoped attributes (request ID, tenant ID). |
| `on_end(span)` | Passed in as a `ReadableSpan`, which is intended to be immutable. | Filtering, enriching, or modifying attributes before export. |
| `on_ending(span)` | Mutable (still in development). | Last-moment attribute changes without the immutability workarounds. |

A common use case is **PII redaction**. You can inspect outgoing spans and remove sensitive values before export. For practical examples, see [Mask and redact data](/docs/phoenix/tracing/how-to-tracing/advanced/masking-span-attributes).

<Warning>
The `ReadableSpan` passed to `on_end` is *intended* to be immutable. In Python you can edit it anyway, but doing so affects every downstream processor and exporter attached to the same Tracer Provider. If you need to modify a span, prefer copying the `ReadableSpan` with edited attributes rather than mutating it in place.
</Warning>

For the full lifecycle details and how `on_end` immutability varies between Python and TypeScript, see the [Span Processor](/docs/phoenix/tracing/concepts-tracing/otel-openinference/span-processor) page.

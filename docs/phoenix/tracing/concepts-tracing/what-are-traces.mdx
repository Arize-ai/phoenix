## How Tracing Works

Under the hood, Phoenix tracing uses two open standards:

* [OpenTelemetry](https://opentelemetry.io/), or OTel, is the open framework for creating and exporting telemetry data. Phoenix accepts OTel spans over OTLP, so the same instrumentation can be exported to other OTel-compatible backends.
* [OpenInference](https://github.com/Arize-ai/openinference) is a set of AI semantic conventions built on top of OTel. It defines the attributes that make traces meaningful for AI applications, such as span kinds, messages, token counts, retrieved documents, tool calls, and cost.

Together, OpenTelemetry and OpenInference give Phoenix [30+ tracing integrations](/docs/phoenix/integrations), portability across OTel-compatible backends, and a standard format for AI trace data. The flow is:

1. **Instrumentation** captures work in your application as spans. You can use an OpenInference integration or add spans manually.
2. **An exporter** sends those spans to Phoenix over OTLP. In Python, Phoenix OTEL's `register()` configures the exporter, and `auto_instrument=True` turns on installed OpenInference instrumentors.
3. **The Phoenix collector** receives the spans, groups them into traces, and shows them in Observe. Use [Explore traces](/docs/phoenix/observe/explore-traces) to inspect, filter, and debug them.

## What's Inside a Trace

A trace contains spans, and each span should have a span kind. The span kind tells Phoenix what operation the span represents. Phoenix falls back to `UNKNOWN` when the value is missing or not recognized.

| Span kind | What it represents |
| :--- | :--- |
| `LLM` | A model call for chat or completion |
| `TOOL` | A tool or function call |
| `AGENT` | An agent run that may contain model, tool, and retrieval spans |
| `RETRIEVER` | A retrieval call that returns documents |
| `CHAIN` | A step that groups related application work |
| `EMBEDDING` | An embedding model call |
| `RERANKER` | A reranking step for retrieved documents |
| `GUARDRAIL` | A safety or policy check on input or output |
| `EVALUATOR` | An evaluation run that scores a model response |
| `PROMPT` | A prompt template rendered with variables |
| `UNKNOWN` | The fallback when no span kind is set or the value is not recognized |

### Span Attributes

Span attributes are key-value pairs that describe a span. Common examples include `llm.model_name`, `llm.input_messages`, `input.value`, and `output.value`.

Attributes can also carry multimodal content, such as image URLs, base64 images, audio URLs, and transcripts. See [Capture multimodal traces](/docs/phoenix/tracing/how-to-tracing/advanced/multimodal-tracing).

Phoenix uses these attributes to show inputs, outputs, tool calls, retrieval details, latency, cost, and errors. Auto-instrumentation sets many attributes for you. Add your own attributes with [Customize your traces](/docs/phoenix/tracing/how-to-tracing/add-metadata/customize-spans). For the full reference, see [Span kinds](/docs/phoenix/tracing/concepts-tracing/otel-openinference/span-kinds) and [Semantic conventions](/docs/phoenix/tracing/concepts-tracing/otel-openinference/semantic-conventions).

Use this page when you have saved ATIF agent runs and want to view them in Phoenix.

If your app is running and you want live traces, [instrument your app](/docs/phoenix/tracing/how-to-tracing/setup-tracing/instrument) instead.

[ATIF (Agent Trajectory Interchange Format)](https://www.harborframework.com/docs/agents/trajectory-format) is an open schema for recording agent execution traces. [Harbor](https://www.harborframework.com/docs), a benchmark harness for evaluating coding agents, can export ATIF for agent runs from tools like **Claude Code**, **OpenHands**, **Gemini CLI**, and **Codex**.

The `phoenix-client` package converts ATIF v1.0 through v1.7 JSON into OpenTelemetry spans and uploads them to Phoenix. The standalone utility uploads traces only. The Harbor plugin also records experiment runs and links them to traces.

## Install

```bash
pip install arize-phoenix-client
```

## Quick start

```python
import json
from phoenix.client import Client
from phoenix.client.helpers.atif import upload_atif_trajectories_as_spans

# Load one or more ATIF trajectory dicts
with open("trajectory.json") as f:
    trajectory = json.load(f)

client = Client()
result = upload_atif_trajectories_as_spans(
    client, [trajectory], project_name="my-agent-eval"
)
print(result)  # Counts of spans received and queued
```

<Info>
If Phoenix is running elsewhere, set `PHOENIX_COLLECTOR_ENDPOINT` (and `PHOENIX_API_KEY` if it has authentication enabled) before creating the client. See [Connect to Phoenix](/docs/phoenix/tracing/how-to-tracing/importing-and-exporting-traces/importing-existing-traces#connect-to-phoenix).
</Info>

## Verify in Phoenix

Open the Phoenix project after upload. You should see an AGENT root span with nested spans for agent steps, model calls, and tool calls.

## What Phoenix creates

Each trajectory becomes one AGENT root. Each fresh agent step becomes an `iteration N` CHAIN span:

```text
assistant                  AGENT
  iteration 1              CHAIN
    gpt-4                  LLM
    search                 TOOL
  iteration 2              CHAIN
    gpt-4                  LLM
```

Phoenix uses the agent, model, or tool name from ATIF. The original step ID stays in `metadata.atif.step_id`.

Multi-turn trajectories add `turn N` AGENT spans between the root and iterations. User prompts, system prompts, and steps marked `is_copied_context: true` add context but do not create execution spans.

An agent step with `llm_call_count: 0` creates no LLM span. It still gets a CHAIN span and any TOOL spans.

## Multi-agent runs

When an agent delegates work to a subagent, upload the parent and child JSON files together, with parents before children. The helper does not read `trajectory_path`, fetch URLs, or load referenced files.

External references resolve by `session_id` before ATIF v1.7 and by `trajectory_id` in ATIF v1.7. For v1.7 external files, include both `trajectory_path` and the child `trajectory_id` in the reference.

```python
with open("parent_trajectory.json") as f:
    parent = json.load(f)
with open("child_trajectory.json") as f:
    child = json.load(f)

# Upload together so cross-references resolve
upload_atif_trajectories_as_spans(
    client, [parent, child], project_name="my-agent-eval"
)
```

When `source_call_id` matches a tool call, the child nests under that TOOL span:

```text
orchestrator               AGENT
  iteration 1              CHAIN
    gpt-4                  LLM
    delegate_task          TOOL
      researcher           AGENT
        iteration 1        CHAIN
          gpt-4            LLM
```

ATIF v1.7 embedded `subagent_trajectories` are included automatically. If no tool call matches, the child attaches to the referencing CHAIN span, or to the parent root if that step has no span.

## Continued runs

When Harbor splits a long agent run across files, include all continuation files in the same batch. Files with a `session_id` ending in `-cont-N` join the original trace.

Continuation roots use `<agent> (continuation N)` and carry `metadata.is_continuation = True`. The Harbor plugin follows local `continued_trajectory_ref` files automatically.

## Details

The details below explain how Phoenix interprets ATIF fields that are not obvious from the span tree. Use them when you need to check reconstructed messages, timing, IDs, or upload limits. For function parameters, see the [Python client API reference](/docs/phoenix/sdk-api-reference/python/arize-phoenix-client).

<AccordionGroup>
  <Accordion title="Messages and observations">
    LLM inputs are reconstructed from ATIF, not copied from provider requests. Every LLM span records `metadata.atif.input_source = "reconstructed"`.

    ATIF sources `user`, `system`, and `agent` map to `user`, `system`, and `assistant` message roles. An observation becomes a tool response only when its `source_call_id` matches a tool call.

    Structured text and image parts remain in serialized messages and tool outputs. The converter does not read or upload media bytes. ATIF v1.8 audio fields are not supported.
  </Accordion>

  <Accordion title="Timing">
    ATIF step timestamps describe events, not durations. A CHAIN span covers the preceding fresh event through its own timestamp.

    Unmeasured LLM and TOOL spans are zero-duration events. The Harbor plugin can add measured LLM durations from `api_request_times_msec` when the measurements match the fresh LLM steps.
  </Accordion>

  <Accordion title="IDs and limits">
    Span IDs are deterministic for the same documents and parent relationships. The standalone helper is not idempotent because Phoenix rejects existing span IDs.

    The converter rejects duplicate span IDs, unresolved span parents, cross-trace parent links, and cycles before upload.

    Very long sessions can exceed OpenTelemetry attribute size limits because each LLM span includes reconstructed conversation history.
  </Accordion>
</AccordionGroup>

## Field mapping

The converter maps ATIF fields to standard [OpenInference](/docs/phoenix/resources/openinference) attributes:

| ATIF field | OpenInference attribute |
|---|---|
| `metrics.prompt_tokens` | `llm.token_count.prompt` |
| `metrics.completion_tokens` | `llm.token_count.completion` |
| `metrics.cached_tokens` | `llm.token_count.prompt_details.cache_read` |
| `metrics.cost_usd` | `llm.cost.total` |
| `agent.model_name` / step `model_name` | `llm.model_name` |
| `agent.tool_definitions` | `llm.tools.{i}.tool.json_schema` |
| `reasoning_content` | `metadata.reasoning_content` |
| `session_id` | `session.id` |
| `trajectory_id` | Root span `metadata.trajectory_id` |
| Step messages | `llm.input_messages` / `llm.output_messages` |
| Tool calls | `llm.output_messages.{i}.message.tool_calls` |
| Observations with a matching `source_call_id` | Tool span `output.value` |
| `final_metrics` | Root span `metadata.final_metrics` |

Agent steps with `llm_call_count = 0` emit TOOL spans without a synthetic LLM span. Only LLM spans carry `llm.*` attributes.

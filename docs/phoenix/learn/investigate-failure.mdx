## Step 1: Check what the agent knew

- Select `search-products` and check the returned product prices in **Output**.
- Select a model call after that search, such as `ChatAnthropic`, and find those results in **Input**.
- Compare the returned prices with the complete recommendation on the **Wonder Toys** span.

In the recorded run, the search returned the kit's \$27.99 price, and that price reached the final model call. The model still recommended the kit while noting that it exceeded the budget.

## Step 2: Define the behavior you want to label

The trace tells us what happened. Before labeling it, let's agree on one question: **did the recommendation respect the shopper's budget?** Use the same rules for every request you review:

- **pass:** Recommended products are below the limit, or the agent explains that no match was found without recommending a more expensive product.
- **fail:** The agent recommends a product at or above the limit without the shopper agreeing to change it.

These are the review criteria for this exercise. A budget label doesn't assess age suitability or whether the products match the requested topic. Record those separately if your notes show a problem. Leave uncertain cases unlabeled and explain what needs checking.

<Accordion title="Ask PXI to define the criteria">
  ```text wrap
  Draft pass/fail criteria for reviewing whether a recommendation respects the shopper's budget. Products must be below the stated limit unless the shopper agrees to change it. An answer that explains no match was found can pass without recommending a more expensive product. Assess other requirements separately and leave uncertain cases unlabeled. Show the criteria without creating a configuration or saving labels yet.
  ```
</Accordion>

## Step 3: Configure the annotation in Phoenix

Now let's make those decisions available in Phoenix. An [**annotation**](/docs/phoenix/tracing/concepts-tracing/annotations-concepts) stores your assessment on a span. An **annotation configuration** defines its name and available labels.

We'll create one called `budget_compliance`. This is our name for the budget review in this exercise. Create it once, then reuse it across the requests you review:

- Open **Settings → Annotations** and check whether `budget_compliance` already exists. If its labels and scores match the settings below, reuse it.
- Otherwise, select **New Configuration**, enter `budget_compliance` as the name, and choose **Categorical** for the type.
- Copy the criteria from Step 2 into **Description** so reviewers can refer to the same rules.
- Set the two category values to `pass` with score `1` and `fail` with score `0`.
- Select **Maximize** for **Optimization Direction**, since a higher score means the budget requirement was met. Select **Create Annotation Config**.
- Open **wonder-toys → Config**. Under **Annotation Configs**, select the checkbox for `budget_compliance` so it appears when you annotate a span.

See [Annotating in the UI](/docs/phoenix/tracing/how-to-tracing/feedback-and-annotations/annotating-in-the-ui) for more about annotation configuration.

<Accordion title="Ask PXI to configure the annotation">
  ```text wrap
  Using the budget criteria we just agreed on, check for a categorical annotation configuration named budget_compliance. Reuse it if its labels are pass = 1 and fail = 0, with optimization direction Maximize. If it is missing or differs, show the proposed changes for approval. Associate the configuration with this trace's project. Do not label any spans yet.
  ```
</Accordion>

## Step 4: Label the request and explain the decision

- Return to the trace and select the top-level **Wonder Toys** span.
- Choose **Annotate this span**. In the `budget_compliance` field, select `pass` or `fail` based on your review. Phoenix saves the label when you select it.
- Select **explain** beside the field, add your reason with the request and relevant price, then select **Save**.

For the recorded \$25 request, the label is `fail`: the final model received the \$27.99 price and still recommended the kit.

<Accordion title="Ask PXI to label this request">
  ```text wrap
  Apply our budget criteria to the request in this open trace. Propose a pass/fail label and an explanation citing the shopper's limit, returned prices, and final recommendation. After approval, save budget_compliance on the top-level Wonder Toys span with annotator kind LLM. Preserve existing reviews and leave uncertain cases unlabeled.
  ```
</Accordion>

**Repeat for each request you reviewed on the previous page:** the \$25, \$35, and \$1 requests. Read each trace before deciding; a different budget can produce a different outcome.

- Save one budget assessment on the top-level **Wonder Toys** span for each request, rather than labeling every model and tool span.
- Include passing requests as well as failures. If the evidence is insufficient, leave the request unlabeled and add a note about what's missing.
- Reuse the configuration from Step 3. You don't need to create it again.

To find your failing requests again, open **wonder-toys → Spans** and enter:

```python wrap
parent_span is None and annotations['budget_compliance'].label == 'fail'
```

The first condition selects top-level spans; the second selects the label you added. The notes and labels are attached to these spans, so use the **Spans** filter here.

Your notes and labels now record how each request handled the budget. Next, [turn those runs into test cases](/docs/phoenix/learn/build-test-cases) so you can check whether a change fixes the problem while preserving answers that already worked.

Use the Prompt Playground to run a prompt against an LLM, change its model settings, compare prompt variants, and run prompts over a dataset.

## Setup

1. [Configure AI Providers](/docs/phoenix/prompt-engineering/how-to-prompts/configure-ai-providers) and set the API key for your provider.
2. In the playground view, write a valid prompt for the LLM.
3. Click **Run** on the top right, or press `mod + enter`.

If the run is successful, the LLM output streams into the **Output** section.

## Prompt Editor

Define the prompt template in the prompt editor, on the left side of the screen. For the template model, see [Prompts Concepts](/docs/phoenix/prompt-engineering/concepts-prompts/prompts-concepts#prompt-templates).

1. Select the template language on the toolbar: **mustache** or **f-string**.
2. Type a variable placeholder in the prompt, for example `{{question}}` for mustache.
3. Fill each variable in the **inputs** section, or fill the variables from a dataset.

Each variable placeholder shows in the **inputs** section. In a dataset, each row supplies key/value pairs for the inputs.

## Model Configuration

Each prompt instance has its own LLM and invocation parameters.

1. Click the model configuration button at the top of the prompt editor.
2. Select the LLM and set the invocation parameters.
3. To keep this configuration across playground sessions, click **save as default**.

<Frame caption="Switch models and modify invocation params">
  <img src="https://storage.googleapis.com/arize-phoenix-assets/assets/gifs/model_config.gif" />
</Frame>

<Info>
For OpenAI and Azure OpenAI models, select the **OpenAI API type** in the model configuration panel. Select **Chat Completions** (`chat.completions.create`) or **Responses** (`responses.create`) for the model and features that you need.
</Info>

### Reasoning / extended thinking

For models that support reasoning, the model configuration panel shows controls for how much the model thinks before it responds:

- **Anthropic** (Claude 3.7 Sonnet and later): set extended thinking to **disabled**, **adaptive** (the default), or **enabled**. With **enabled**, set an explicit `budget_tokens` value and a visibility toggle. You can also set the output **effort** (`high` / `medium` / `low`). When you enable extended thinking, Phoenix increases `max_tokens` to a minimum of `budget_tokens + 1`.
- **Google** (Gemini 2.5 models): set `thinkingBudget`, `thinkingLevel` (`low` / `medium` / `high`), or both.

Higher thinking budgets and effort levels can improve quality on difficult tasks, but they increase latency and token use. Start with the defaults. Increase them only when a task needs more reasoning.

## Comparing Prompts

Compare multiple prompt variants in the playground. The UI labels the variants A, B, C, and D.

1. Click **+ Compare** at the top of the first prompt to add a duplicate instance.
2. Change the template, model, or parameters of each variant. Each variant keeps its own settings.
3. Click **Run** to compare the outputs, or run an experiment to find the best prompt and model configuration for the task.

## Using Datasets with Prompts

Run one or more prompts on each example in a dataset.

1. [Load a dataset](/docs/phoenix/datasets-and-experiments/how-to-datasets) that contains the input variables of your prompt template.
2. Click **Run**.

Phoenix applies each configured prompt to each dataset example. It invokes the LLM for all prompt-example combinations. Phoenix records the results as an experiment on the loaded dataset. See [Playground Traces](/docs/phoenix/prompt-engineering/how-to-prompts/using-the-playground#playground-traces).

<Frame caption="Each example's input is used to fill the prompt template">
  <img src="https://storage.googleapis.com/arize-phoenix-assets/assets/images/phoenix-docs-images/6587d15c-image.jpeg" />
</Frame>

The table shows each example's **input** and **reference output** beside the tasks' columns. Use **Columns** in the experiment toolbar to show or hide those and the example's **metadata**. Metadata starts hidden unless the loaded examples carry some, your choice is remembered in the browser, and the metadata cell leaves out the `annotations` key that holds expected outputs recorded for evaluators until you turn off **Hide expected annotations** in the experiment settings.

### Configuring Dataset Paths

For prompt tasks, the playground reads template variables from `input` by default, so `{question}` resolves against `input.question`. Evaluator tasks start at the example root instead, because an evaluator's input mapping addresses `input`, `output` and `metadata` directly. The path is remembered per dataset for each kind of task, so changing it for prompts leaves the evaluators' path alone. If your dataset examples keep prompt inputs in a different nested object, set the path:

1. Load a dataset.
2. Click the **settings button** (gear icon) in the experiment toolbar, next to the dataset selector.
3. Set **Prompt variable path** to the dot-notation path that contains your template variables, for example `input` or `payload.inputs`.

Phoenix then resolves template variables against that object. For example, your prompt uses `{question}` and your dataset example is:

```json
{
  "input": {
    "question": "What is the weather in San Francisco?"
  }
}
```

For this example, keep the default prompt variable path, `input`.

To refer to root-level fields directly, for example `{input.question}` and `{output.response}`, clear the prompt variable path. Variables then resolve from the root object. For this dataset example:

```json
{
  "input": {
    "question": "What is the weather in San Francisco?"
  },
  "output": {
    "response": "I can help with that."
  }
}
```

use template variables such as `{input.question}` and `{output.response}` in your prompt.

### Naming the Experiment

1. Click the **settings button** (gear icon) in the experiment toolbar.
2. Optional: enter a **Name** and a **Description** for the next experiment that you run.

If you leave **Name** empty, Phoenix uses the generated default name. To change the name or description after the run, open the experiment action menu in the dataset experiments table and select **Edit**.

## Appending Conversation History

<video controls autoPlay={false} loop={false} width="100%">
  <source src="https://storage.googleapis.com/arize-phoenix-assets/assets/videos/append_messages_on_playground.mp4" type="video/mp4" />
</video>

When you run experiments over datasets, you can append conversation messages from your dataset examples to the prompt. Use this to:

- **A/B test models**: compare how different models respond to the same conversation history.
- **Test system prompts**: evaluate different system prompts against the same user conversations.
- **Run multi-turn conversation experiments**: run experiments on existing conversation threads.

### Setting the Appended Messages Path

1. Load a dataset that contains conversation messages in OpenAI format.
2. Click the **settings button** (gear icon) in the experiment toolbar, next to the dataset selector.
3. Enter the **dot-notation path** to the messages array in your dataset examples, for example `messages` or `input.messages`.

When you run the experiment, Phoenix appends the messages at that path to the **end of your prompt template**. It does this after it applies the template variables. Thus you can keep your system prompt and initial instructions in the template and replay real conversation history from the dataset.

### Dataset Format

Your dataset examples must contain messages in the OpenAI chat format:

```json
{
  "messages": [
    {"role": "user", "content": "What is the weather in San Francisco?"},
    {"role": "assistant", "content": "Let me check that for you."},
    {"role": "user", "content": "Thanks! Also, what about New York?"}
  ]
}
```

Supported message roles:

| Role | Content |
| --- | --- |
| `user` | User messages |
| `assistant` | Assistant/AI responses |
| `system` | System messages |
| `tool` | Tool response messages (with `tool_call_id`) |

For nested structures, use a dot-notation path:

```json
{
  "input": {
    "messages": [
      {"role": "user", "content": "Hello!"}
    ]
  }
}
```

For this example, set the path to `input.messages`.

### Example: A/B Testing System Prompts

1. Create a dataset with conversation examples (user messages and expected context).
2. In the playground, configure two prompt variants (A and B) with different system prompts.
3. Load your dataset and set the appended messages path to `messages`.
4. Run the experiment to compare how each system prompt handles the same conversations.

Use this procedure to evaluate prompt changes across many real conversations.

## Playground Traces

Phoenix records all LLM invocations from the playground. Use these records for analysis, annotations, evaluations, and dataset curation.

If you run an LLM with free-form inputs (no dataset), Phoenix records the spans in a project named "playground".

## Comparing evaluators

The playground holds one mode at a time: prompts and decisions, which are tested and can be compared side by side, or evaluators, which judge them and run alone. The task selector at the top of each task (where the prompt picker sits) has a **Prompts**, a **Decisions** and an **Evaluators** tab: each lists your saved items of that kind, with **New prompt**, **New decision**, or **New LLM evaluator** and **New code evaluator**, beneath them. Picking a decision loads its latest version, and a version and tag picker beside the selector loads another. Picking an evaluator turns the page into an evaluator playground where you try LLM and code evaluators against a dataset, record the outputs you expected, and compare up to four evaluators side by side. You can also open an evaluator here with the **Playground** button of the evaluators, dataset evaluators and project evaluators tables, or from the evaluator picker of a prompt task. From a project's evaluators the playground opens without a dataset; select one to run the evaluator over its examples.

1. Pick an evaluator, or start a new one, from the task selector of the first task. While the page holds more than one task, the selector only offers the page's mode (prompts and decisions, or evaluators); remove the other tasks to switch between them.
2. Configure the evaluator's tabs. An LLM evaluator's **Prompt** tab is its judge prompt, with the same model controls as a prompt task; a code evaluator's **Code** tab needs a configured sandbox. **Input mapping** points the evaluator's variables at fields of the dataset example, and **Output** names the evaluator and its labels or score.
3. In the **Experiment** panel, select a dataset and optional splits. Evaluators run over every example of the dataset, or of the selected splits.
4. Click **Compare** to add a second, third and fourth evaluator, either a saved one, a new draft, or a duplicate of the current task.
5. Click **Run**. Every task runs over the dataset as its own experiment, so evaluator runs get the same queueing and retries as prompt experiments. The play button in an evaluator's column header runs only that evaluator over every example, and follows **Record** like **Run**. The play button at the start of a row runs every task on that one example as a spot check: it is never recorded, whatever **Record** says, and the column keeps the experiment of its last full run. Inspect labels, scores, explanations, and errors in the table, and open an evaluator's trace from its cell.
6. Record what you expected. Thumbs up accepts an evaluator's result as the expected output; thumbs down opens a form for the label or score that was expected. The band under each result shows the expected output and flags results that differ from it. Each evaluator's column header counts the examples with an expected output and how many results agree with it.
7. Edit an evaluator and run again; the columns of the other evaluators keep their results.
8. To keep an evaluator, click **Save**. The dialog asks for a name and description (the same name as in **Output**) and states what will happen: a new draft becomes an evaluator attached to the selected dataset, an evaluator already on the dataset is updated in place, and a code evaluator from elsewhere is updated and added to the dataset. Click **Save as new** to leave a loaded evaluator unchanged and save a copy named after it with a `_copy` suffix, which you can rename later. Saving needs a selected dataset.

With **Record** on, an evaluator run is a recorded experiment: it appears in the dataset's experiments list and in the experiment compare view, with the evaluator's verdicts as annotations named after the evaluator. With **Record** off the experiment is temporary and Phoenix removes it later.

An evaluator task judges the dataset example itself: its context is the example's `input`, `output` and `metadata`, and there is no `reference`. Use **Input mapping** to point evaluator variables at other fields; a template that names `reference` needs a mapping of its own. Expected outputs are stored on the dataset example as human annotations under the `annotations` key of its metadata, named after the evaluator (or `evaluator.output` for an evaluator with several outputs), so evaluators with the same name share them. They are written in batches as new dataset versions and are never passed to the evaluators. **Stop** stops the running experiments; requests already running may finish.

## Editing the examples

Press **Edit** in the Experiment toolbar to change the dataset without leaving the playground, or press the pencil that appears over an example's input, reference output or metadata cell to start editing right there. Each of those cells opens a JSON editor when pressed; the toolbar along the bottom adds examples, removes them, and saves everything as one new dataset version. Runs wait until you save or cancel, since they judge the saved examples rather than the ones on screen. Expected outputs recorded on an example are kept through a metadata edit even while the table hides them.

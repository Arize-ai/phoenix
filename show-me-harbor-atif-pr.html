Tracing model

From Harbor ATIF files to one Phoenix trace

After a Harbor trial finishes, the plugin reads its saved trajectory graph, replaces producer IDs in memory, and turns fresh ATIF operations into a causal span tree. Copied history rebuilds prompts but creates no execution spans. The Harbor adapter controls equal-time display order at upload, without invented timestamps or a Harbor-specific UI rule.

Who owns what Harbor runs the trial and writes ATIF. The converter builds the semantic span order. The Harbor adapter reverses the upload batch to match Phoenix's existing query order. The importer never writes to the ATIF files.

Single-step trial

Read the canonical agent/trajectory.json. Add user-agent/trajectory.json only for simulated-user trials.

Multi-step, no resume

Read one canonical file for every attempted step, in Harbor result order. Unattempted step folders are ignored.

Multi-step with resume

The last available step file is cumulative. Import only that snapshot to avoid duplicate history.

Referenced graph

Follow local continuations, embedded subagents, and file-backed subagents. Shared files load once; cycles stop.

trial-root/ ├── agent/trajectory.json # single-step canonical root ├── user-agent/trajectory.json # simulated user, when configured └── steps/ ├── prepare/agent/trajectory.json # attempted step └── solve/agent/trajectory.json # final cumulative snapshot if resume=true

Source interval

The source CHAIN starts at the preceding fresh event and ends at its own ATIF timestamp. Missing or backward clocks collapse to a point.

LLM timing

Harbor's api_request_times_msec sidecar can measure an LLM inside that interval. The adapter applies it only when every request matches one LLM step; otherwise the LLM is a point event.

Tool timing and display

ATIF has no tool duration. Tools stay point events at the exact step timestamp. Harbor reverses the upload batch, Phoenix returns descending insertion order, and the stable timestamp sort preserves that order on exact ties.

Bugs here can read files outside the trial, attach the wrong trace, or break replay.

File access
Trajectory references

A trajectory can point at ../../.env, an absolute path, a symlink outside the trial, or a URL that contains credentials.

_load_file resolves the real path and requires it to remain inside the current Harbor role directory. It accepts regular JSON files only. _local_reference rejects remote and absolute references, then sanitizes remote values before logging them.

The loader has no explicit file-size, document-count, or recursion-depth limit. A huge acyclic graph can still consume substantial memory.

Identity
Producer ID reuse

Agents may omit trajectory_id, reuse one session across steps, or emit a constant session. Phoenix could merge trials, reject duplicate span IDs, or group unrelated trials into one session.

The importer replaces both IDs in memory. Trajectory identity includes the job, trial, role, step, path, and embedded-child position. It keeps producer IDs in metadata. If Phoenix already stores an unexpected span under the trace ID, confirm_trace refuses the link.

Two independent ingesters must not assign the same Harbor job and trial identity to different data. Hash collisions are far less likely than an identity bookkeeping error.

Harbor contract
Root selection

Importing every step when the last file already contains cumulative history duplicates spans. Importing only the last file when steps are independent loses earlier activity.

Without resume, _root_locations imports every attempted step in Harbor result order. With resume_trajectory=true, it imports the last available cumulative snapshot. It ignores unattempted and stale files.

This depends on Harbor's current storage behavior. If Harbor changes what a resumed step file contains, this selection rule must change with it.

Graph shape
Broken subagent links

A missing or invalid child trajectory can leave a subagent reference pointing nowhere. The converter could produce a disconnected tree or attach the child to the wrong tool call.

The loader rewrites valid file references to the loaded child's unique trajectory ID and removes ambiguous session keys. It removes unresolved path-only references. Reparenting keeps valid internal parents and attaches dangling roots to harbor.trial.

The trace stays connected, but it can lose causality. A child may appear under the trial root instead of the tool call that launched it.

Replay
Partial span upload

Phoenix rejects a request that includes an existing span ID. A timeout can also leave the client unsure whether Phoenix queued the spans.

confirm_trace compares expected and stored IDs, filters the missing set, reverses that batch, and checks received and queued counts. A retry after an interrupted prefix preserves final display order. After an exception, the plugin queries again and accepts the trace only if the stored set now matches.

A partial acceptance can leave orphan spans. If the plugin then records a successful run without a trace, replay cannot add the link because successful runs are immutable.

Equal-time order
LLM before tools

ATIF gives tools no start or end time. Equal timestamps make a normal chronological sort depend on the order Phoenix returns the rows.

The converter lists the LLM before its tools and tools in declared array order. Harbor uploads that list in reverse. Phoenix inserts FIFO and returns descending row IDs, so its existing stable start-time sort restores the converter order. No server, schema, GraphQL API, or Harbor-specific frontend logic changes.

This display rule depends on Phoenix retaining its current insertion and query order. Declared tool order still does not prove serial execution.

Write order
Trace before run

Creating the run first would make later trace attachment impossible. Uploading the trace first can leave an orphan trace if run creation then fails.

The plugin confirms the trace before calling log_run. If run creation fails, Harbor stops and preserves its terminal result. A resumed job finds the existing spans and can retry run creation.

An orphan trace may exist until resume succeeds. A successful run recorded without a trace stays untraced under that Harbor job.

Coverage
Best-effort tracing

An untraced run can look like a trial with no agent activity even when ATIF loading or upload failed.

Trace errors produce warnings but do not discard the experiment run, rewards, or evaluations. Valid roots still load when another canonical root is missing.

Phoenix has no queryable trace_import_ok field in this PR. Logs carry the reason. Measuring trace coverage requires separate work.

Retry contract
Terminal attempt detection

The plugin could ingest an attempt that Harbor plans to retry, or skip the final attempt, if its retry calculation differs from Harbor's.

The plugin counts trial-start events and applies Harbor's include, exclude, cancellation, and maximum-retry rules before recording a trial-end event.

This mirrors Harbor behavior instead of consuming a public terminal-attempt event. A Harbor retry change can require a plugin update.

Concurrency
One ingester per job

Two processes can discover that the same experiment or spans are missing, then try to create them at the same time.

An async lock serializes trial recording inside one plugin instance. Run-conflict recovery and span requery handle several races after Phoenix responds.

The lock does not coordinate separate processes or machines. Experiment discovery and creation are not atomic. Operate one ingester for each Harbor job.

Meaning
Error versus reward

A failed task and a failed runtime are different. Treating a verifier reward of zero as a trace error would mix agent quality with infrastructure health.

The harbor.trial root uses the same collected exceptions as the run error and infra_ok. Rewards remain evaluations, even when a step also raised an exception.

Converted child spans generally remain OK. The trial root carries Harbor's infrastructure failure, so reviewers should read root status and evaluations together.
